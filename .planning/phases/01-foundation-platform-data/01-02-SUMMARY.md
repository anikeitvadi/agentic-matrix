## Deviations from Plan

### Auto-Fixed Blocking Issues (Rule 3)

**1. Velite slug schema incompatibility**
- **Found during:** Task 1 - Initial Velite build
- **Issue:** Schema used `s.slug('platforms')` which requires slug in frontmatter but also auto-generates from path, causing validation errors
- **Fix:** Changed to `s.path()` with `.transform()` to extract filename as slug
- **Files modified:** velite.config.ts
- **Commit:** Included in Task 1 commit (89b652c)

**2. Velite s.mdx() static build incompatibility**
- **Found during:** Task 2 - Production build
- **Issue:** `s.mdx()` outputs JavaScript code strings in JSON files, which cannot be executed in static builds. Build failed with "Invalid tag" errors when trying to render MDX body as React component
- **Fix:** Changed `s.mdx()` to `s.markdown()` in velite.config.ts for both platforms and policies collections. Updated components to render HTML with `dangerouslySetInnerHTML`
- **Files modified:** velite.config.ts, components/platform/PlatformProfile.tsx, app/editorial-policy/page.tsx
- **Commit:** Included in Task 2 commit (3d637e6)
- **Rationale:** Velite MDX compilation to JSON produces code strings that need runtime evaluation. Markdown compilation produces safe HTML that works with static generation. Content is from trusted MDX files, not user input, so dangerouslySetInnerHTML is safe.

**3. Editorial policy page JSX syntax error**
- **Found during:** Task 2 - Production build
- **Issue:** app/editorial-policy/page.tsx had mismatched JSX tags (div/main) and tried to render MDX body as component, blocking build
- **Fix:** Changed to use `dangerouslySetInnerHTML` pattern matching platform pages
- **Files modified:** app/editorial-policy/page.tsx
- **Commit:** Included in Task 2 commit (3d637e6)
- **Note:** This file was created by another plan but blocked this plan's build verification

## Technical Insights

### Velite MDX vs Markdown Trade-off
The switch from `s.mdx()` to `s.markdown()` resolved the static build issue but has implications:

**Pros:**
- Works with static generation out of the box
- Simpler build pipeline (no runtime MDX complexity)
- HTML output is cacheable and performant
- No client-side JavaScript needed for content rendering

**Cons:**
- Cannot use interactive React components in content
- No MDX component customization at render time
- HTML output slightly larger than MDX tree

**Decision:** For Phase 1 platform profiles, plain markdown/HTML is sufficient. Content is primarily text paragraphs without interactive elements. If future phases need interactive MDX components, we can revisit with custom MDX loader or client-side compilation.

### Next.js 16 Async Params Pattern
Plan correctly anticipated Next.js 16 requirement to `await params` in dynamic routes. This pattern is enforced at build time and prevents common bugs around async route params. All platform detail pages follow this pattern correctly.

### Static Generation Performance
All 5 platform pages pre-render to static HTML at build time. This provides:
- Instant page loads (no server rendering delay)
- Zero database/CMS queries at request time
- Optimal SEO (content present in initial HTML)
- CDN-friendly (can serve from edge)

Future platform additions will automatically benefit from static generation via `generateStaticParams`.
