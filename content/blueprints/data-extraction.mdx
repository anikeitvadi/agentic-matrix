## Overview

Data extraction agents transform unstructured documents into structured, validated data—automating manual data entry for invoices, forms, emails, contracts, and receipts. This blueprint focuses on **validation-first architecture** where schema definition precedes extraction, enabling confidence scoring and human review workflows.

**Best suited for:** Organizations processing high volumes of documents with consistent structure but variable formatting (AP automation, loan applications, insurance claims, HR onboarding).

**Key business value:** 70-80% reduction in manual data entry time, improved accuracy over human transcription, audit trail for compliance.

**Key patterns:**

- **Schema-first design:** Define Zod schemas for extracted data before building extraction logic
- **Confidence scoring:** Track per-field confidence (0-1 scale), trigger human review when below threshold
- **Multi-stage validation:** Format validation (regex, enums) → Business rules (totals match, dates logical) → Human review (if low confidence)
- **Batch processing:** Queue documents for async processing to handle volume spikes

## Platform-Specific Considerations

**Anthropic Claude (Recommended):** Vision API natively handles PDFs with text and layout understanding—no separate OCR step for native PDFs. Extended thinking mode valuable for complex documents (multi-page invoices with line items). Prompt caching reduces cost for repeated schema definitions across batches.

**Amazon Bedrock Agents (Recommended):** Integrates with Amazon Textract for OCR (handles scanned documents, handwriting). Built-in guardrails prevent hallucination in extraction. Natural S3 integration for document storage and batch processing via SQS.

**OpenAI Frontier:** Vision API supports document analysis. Function calling with structured outputs enforces schema compliance. Consider GPT-4o for complex layouts, GPT-4 mini for simple forms (cost optimization).

**Google Vertex AI:** Document AI has pre-trained parsers for common document types (invoices, receipts, forms)—faster than training custom models. Vision API for general documents. Natural integration with GCS for storage.

## Document Processing Patterns

### Pattern 1: PDF Layout Understanding (Native PDFs)

For digitally-created PDFs (not scanned):

- **Claude Vision / OpenAI Vision:** Send PDF directly to vision-enabled model with schema in prompt
- **Advantage:** Understands table structure, multi-column layouts, headers/footers
- **Chunking strategy:** Multi-page documents—extract by page, then merge data (specify page context in prompts)
- **Limitation:** Max 32 pages per call (Claude), may need page sampling for very long documents

### Pattern 2: OCR Pipeline (Scanned Documents)

For scanned documents or images:

1. **Preprocessing:** Deskew, denoise, increase contrast (OpenCV, ImageMagick)
2. **OCR extraction:** Amazon Textract, Google Document AI, Tesseract
3. **Post-OCR validation:** Check for common OCR errors (O→0, I→1), confidence scores per word
4. **Agent extraction:** Feed OCR text + bounding boxes to LLM for structured extraction

**Warning:** OCR quality degrades with handwriting, low-resolution scans, complex backgrounds. Always include confidence scoring and human review for OCR pipelines.

### Pattern 3: Multi-Page Document Handling

For documents spanning multiple pages (invoices with line items, contracts):

- **Page-by-page extraction:** Process each page independently, track page metadata
- **Hierarchical schemas:** Top-level document fields (invoice number, date) + array of line items (description, amount, quantity)
- **Cross-page validation:** Verify totals match across pages, flag inconsistencies for review
- **Example schema:**

```typescript
const InvoiceSchema = z.object({
  metadata: z.object({
    invoiceNumber: z.string(),
    date: z.string().date(),
    vendorName: z.string(),
    totalAmount: z.number(),
  }),
  lineItems: z.array(
    z.object({
      description: z.string(),
      quantity: z.number(),
      unitPrice: z.number(),
      amount: z.number(),
      page: z.number(), // Track which page item came from
    })
  ),
  confidence: z.object({
    overall: z.number().min(0).max(1),
    perField: z.record(z.number()),
  }),
})
```

### Pattern 4: Batch Processing for High Volume

For processing hundreds or thousands of documents daily:

- **Queue architecture:** S3 upload triggers Lambda/Cloud Function → publishes to SQS/Pub Sub → workers process batch
- **Parallel processing:** Multiple workers pull from queue, process independently
- **Dead letter queue:** Failed extractions (malformed documents, timeouts) routed to DLQ for manual review
- **Monitoring:** Track queue depth, processing time per document, error rates

## Schema Design

**Validation-first approach:** Define your data schema before building extraction logic. Prevents scope creep and enables automatic validation.

### Field-Level Confidence Tracking

```typescript
type ExtractedField<T> = {
  value: T
  confidence: number // 0-1 scale
  source: 'extracted' | 'inferred' | 'defaulted'
  boundingBox?: { page: number; x: number; y: number; width: number; height: number }
}

type ExtractedInvoice = {
  invoiceNumber: ExtractedField<string>
  date: ExtractedField<Date>
  totalAmount: ExtractedField<number>
  vendorName: ExtractedField<string>
  // ... other fields
}
```

**Confidence thresholds:**

- 0.9+: Auto-approve (high confidence)
- 0.7-0.9: Automatic extraction, flag for spot-check review
- Below 0.7: Queue for human review before database insert

**Calibration:** Test thresholds on sample dataset, adjust based on false positive/negative rates.

### Business Rule Validation

Beyond format validation, encode business logic:

```typescript
const InvoiceBusinessRules = z.object({
  invoiceNumber: z.string().regex(/^INV-\d{6}$/),
  date: z.string().date().refine((date) => {
    const invoiceDate = new Date(date)
    const today = new Date()
    const sixMonthsAgo = new Date()
    sixMonthsAgo.setMonth(today.getMonth() - 6)
    return invoiceDate >= sixMonthsAgo && invoiceDate <= today
  }, "Invoice date must be within last 6 months"),
  lineItems: z.array(z.object({
    quantity: z.number().positive(),
    unitPrice: z.number().positive(),
    amount: z.number(),
  })).refine((items) => {
    // Validate line item amounts match quantity * unitPrice
    return items.every(item =>
      Math.abs(item.amount - (item.quantity * item.unitPrice)) < 0.01
    )
  }, "Line item amounts must match quantity × unit price"),
  totalAmount: z.number().positive(),
}).refine((invoice) => {
  // Validate total matches sum of line items
  const lineItemTotal = invoice.lineItems.reduce((sum, item) => sum + item.amount, 0)
  return Math.abs(invoice.totalAmount - lineItemTotal) < 0.01
}, "Total amount must match sum of line items")
```

## Common Mistakes to Avoid

**Extraction before validation:** Building extraction logic without defining schemas leads to inconsistent outputs and scope creep. Define Zod schemas first, then build extraction to match.

**Ignoring confidence scores:** Treating all extractions as equally reliable causes downstream errors. Always track per-field confidence and implement review thresholds.

**Poor chunking for multi-page documents:** Processing entire 50-page contracts as single prompt hits token limits and loses context. Extract page-by-page with explicit page numbers, merge structured data afterward.

**No OCR quality checks:** Scanned documents have variable quality—processing without checking OCR confidence leads to garbage-in-garbage-out. Validate OCR confidence per word, flag low-confidence documents for manual processing.

**Missing business rule validation:** Format validation (is this a number?) isn't enough. Encode domain logic (invoice total = sum of line items, dates are logical, amounts are positive) to catch extraction errors.

**Over-reliance on examples:** Few-shot prompting with 5-10 examples works for simple cases but doesn't scale to document variations. Use schema-driven extraction with clear field descriptions instead of example-heavy prompts.

**No human review workflow:** Even 95% accuracy means 1 in 20 documents has errors. For business-critical data (AP automation, compliance), always include human review for low-confidence extractions.

## Document Type Guidance

### Invoices

**Characteristics:** Structured layout, tables with line items, totals require cross-validation

**Key fields:** Invoice number, date, vendor, line items (description, quantity, price), subtotal, tax, total

**Challenges:** Multi-page invoices, nested line items, currency variations

**Recommended approach:** Hierarchical schema with line item array, validate totals match, confidence threshold 0.85+

### Emails

**Characteristics:** Unstructured text, variable formatting, embedded signatures/disclaimers

**Key fields:** Sender, recipient, subject, date, body text, extracted intent, entities (names, dates, amounts)

**Challenges:** Email threads (multiple responses), forwarded messages, HTML formatting

**Recommended approach:** Extract structured data (metadata) + classify intent + entity extraction, confidence threshold 0.75+ for classification

### Forms

**Characteristics:** Fixed layout, labeled fields, checkboxes/radio buttons, handwritten entries (sometimes)

**Key fields:** Varies by form type—personal info, dates, selections, signatures

**Challenges:** Handwritten text (low OCR accuracy), checkboxes (hard to detect), incomplete forms

**Recommended approach:** Layout-based extraction (field labels as anchors), OCR confidence per field, human review for handwritten sections

### Contracts

**Characteristics:** Long documents (20-100 pages), legal language, defined sections, key terms scattered

**Key fields:** Parties, effective date, termination date, payment terms, obligations, renewal clauses

**Challenges:** Length (token limits), variable structure, legalese interpretation

**Recommended approach:** Multi-pass extraction (metadata first, then section-by-section for key terms), summarization for context, confidence threshold 0.9+ for legal commitments
